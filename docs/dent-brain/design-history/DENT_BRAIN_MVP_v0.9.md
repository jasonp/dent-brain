## Problem Statement

v0.7 is architecturally sound but sized for an 11-phase build before any team member touches the system. Steve Broback is available to alpha now. The primary risk identified in this office-hours session is **team adoption**, not architecture — the plan needs to get a real user doing real work as fast as possible, not build nine phases of machinery speculatively. MVP v0.8 keeps the core value prop of v0.7 (compiled entity pages with typed sections, not raw timelines) and cuts the parts that don't need to exist before Steve validates the shape: stream ingestors, intelligence skills, dream-cycle, server-side Dropbox cron, Gmail scheduled ingest, Granola ingest.

**On hallucination risk:** LLM-synthesized compiled-truth sections are kept in MVP. The alternative — timeline-only pages — ships a log, not a brain. Compiled truth is the token-efficient surface that makes day-to-day queries ("did we pitch Mike?") fast and useful. The risk of hallucinated confirmed facts is accepted for MVP with guardrails: mandatory source-tag backlinks on every synthesized claim, `/flag-fact` skill for fast correction, and a correction log that drives prompt iteration. The mechanical corroboration rubric discussed in this session (structured claims corroborated by ≥2 evidence records) remains the post-MVP hardening path — we tighten the authority surface once Steve has flagged enough bad facts to give us a calibration signal.

## Status Quo

Dent's knowledge currently lives in:
- A shared Dropbox folder that the team appends to but nobody queries as a corpus.
- Gmail threads scoped to each team member's inbox with no shared view.
- Meeting notes in Granola, per-user, non-shared.

The cost of the status quo is visible every time the team asks "did we already pitch X?", "what did Mike say last month?", or "who's been talking to LeadingAgile." These are currently answered by Slack threads, back-reads, or silence.

## Premises

These are the load-bearing assumptions. Each was challenged in this office hours session.

1. **The evidence-log-first architecture from v0.7 is correct.** Append-only evidence records with typed entity views solve the multi-writer, imports-blow-up-mutable-designs, compiled-truth-hides-uncertainty problems. Agreed.

2. **Compiled truth ships in MVP with guardrails; mechanical hardening comes later.** The token-efficiency and day-to-day utility of compiled entity pages is too valuable to defer. MVP uses LLM synthesis for confirmed facts, working inferences, and conflict detection. Guardrails: every synthesized claim carries source-tag backlinks, `/flag-fact` enables one-click correction, and a correction log drives prompt iteration. Post-MVP hardening path: migrate confirmed-facts to mechanical extraction (structured claims corroborated by ≥2 evidence records, no LLM prose in the authority surface) once correction-log data tells us where the prompts fail. Revised this session after pushback.

3. **Steve is enough to validate MVP.** One real user doing real Dent work is worth more than 11 phases of machinery. If Steve uses it and wants Jeff on it, we expand. If Steve bounces off it, we learn why before building more. Agreed.

4. **Proactive `/append-evidence` suggestion is core, not optional.** Asking users to remember to invoke a skill is a losing pattern. The signal-detector skill that reads Cowork session context and suggests the append is the actual UX. Added this session.

5. **Materializer synthesis is in MVP.** Confirmed facts, working inferences, open questions, conflicts, and timeline all ship in MVP. Synthesis is LLM-driven. Guardrails enumerated in premise 2. Hallucination risk is accepted and Steve is the primary detector via `/flag-fact`. Revised this session.

6. **Bulk Dropbox import must happen before MVP ships to Steve.** An empty brain is not testable. The import is also the first real stress-test of classification and entity detection. Agreed.

## Approaches Considered

### Approach A: Ship v0.7 as written, with corrections
Push through all 11 phases before first user contact. Correct the confirmed-facts synthesis mechanism along the way.
- Pros: complete system at end.
- Cons: ~3 months of dark work before Jeff/Steve touch anything. High risk that the shape is wrong for actual Dent workflow. Signal-detector pattern not in scope until very late.

### Approach B: Ship narrowest useful wedge to Steve (RECOMMENDED, revised)
Evidence log + LLM-synthesized compiled entity pages (confirmed facts, inferences, open questions, conflicts, timeline) + Dropbox bulk import + signal-detector + `/append-evidence` + `/flag-fact` + non-technical install. No streams, no intelligence skills, no dream cycle, no server-side cron ingest. Steve on it in ~3-4 focused build weeks.
- Pros: real user validates real behavior on the actual product (compiled brain, not a log). Signal-detector ships as core MVP UX. Correction log from `/flag-fact` directly drives the post-MVP mechanical-corroboration hardening.
- Cons: hallucination risk in confirmed-facts is accepted, mitigated by source-tag backlinks + `/flag-fact`. Materializer cost needs monitoring as evidence density grows. Dropbox classification quality is still the primary ingest-failure surface.

### Approach C: Notion/Airtable substrate
Skip custom evidence log entirely. Use Notion as the data layer; skills read/write Notion API.
- Pros: fastest to ship. Free UI for team.
- Cons: kills gstack-substrate thesis and portability story. Tied to Notion's performance ceiling. Migration cost later is high. Not interesting to build.

## Recommended Approach: B

**Why:** v0.7's architecture is right. The risk isn't architectural, it's adoption and ingest-quality. Approach B puts both in front of Steve as fast as possible while shipping the actual value prop (compiled entity pages, not a log). v0.7's typed-sections design is preserved in MVP; the change is that LLM synthesis runs the sections instead of mechanical rules. Mechanical rules become a v1 hardening pass driven by `/flag-fact` data. Nothing in MVP v0.8 contradicts v0.7's long-term targets.

## FileMaker Federation (new in v0.9)

The Dent team has an existing FileMaker database that is the canonical source of structured CRM data. Steve has connected his Claude to this DB via an MCP connector. The same connector is available to all team members. Dent Brain federates with FileMaker rather than duplicating its data.

### What lives where

| Data | Authoritative source | Why |
|---|---|---|
| Person identity (name, email, LinkedIn, company, address, comm prefs) | **FileMaker — `People` table** | FM has been the source for years. Mutating it from two places risks drift. |
| Tags / topical interests per person | **FileMaker — `Tags` + `Tags People`** | Tags are structured; FM's lookup performance beats rebuilding our own taxonomy. |
| Conference registration history | **FileMaker — `Event Registration`, `Past Registrations`, `Past Conf People`** | Tied to payments. Authoritative in FM. |
| Hotel registrations + room nights | **FileMaker — `Hotel Registrations`, `NightStays`** | Same. |
| Payments / purchases | **FileMaker — `HR Purchases`, `RHR Purchases`, `Purchase MP`** | Financial source of truth. Never owned by Dent Brain. |
| Outbound communications log | **FileMaker — `Communication Items`, `Email Items`, `Email Stats`** | Already tracked there. |
| Historical CRM notes (Notes Q, Sticky Notes) | **FileMaker — `Notes Q`, `Sticky Notes`** | Continues to be Steve's quick-capture surface. Dent Brain may *also* ingest these read-only as evidence (see below). |
| Meeting notes, email threads, observations from team members | **Dent Brain — evidence log** | New unstructured data the FM schema isn't built for. |
| Working inferences, open questions, conflict detection across multiple sources | **Dent Brain — materializer** | Synthesis layer. Not in FM. |
| Speaker pipeline narrative, session planning, retros | **Dent Brain — namespace pages** | Markdown is the right shape. |

### The federation pattern (lazy reads, not import)

We do NOT import FileMaker into Dent Brain. Importing creates a stale-cache problem: registrations, payments, and tags change in FM constantly with no reverse-flow.

Instead:
- **Each Dent Brain user installs both MCP connectors in Cowork**: Dent Brain (this project) + FileMaker (Steve's existing connection, made shareable). Skills and intelligence agents call both.
- **Entity pages reference FM IDs.** A person entity page header includes `filemaker: { record_id: 12345 }`. Skills resolve that ID against FM at query time.
- **Materializer does NOT inline FM data on every rebuild.** Reasons: (a) FM data changes between rebuilds and inlining creates staleness, (b) materializer cost stays bounded, (c) FM rate limits / latency don't block evidence rebuilds. Instead, the materializer leaves a "linked record" pointer.
- **Read-time enrichment.** When a skill answers a query about a person ("what's Mike's company?"), it fetches the FM record live, combines with Dent Brain's evidence-derived sections, and answers. The user sees one merged view.
- **One-way write boundary in MVP.** Dent Brain never writes to FM. New observations land in evidence; promoting a new contact to a FM People record stays a manual action Steve takes in FM directly. Two-way write integration is a v2 conversation.

### Historical FM Notes import (one-time, into evidence log)

`Notes Q` and `Sticky Notes` in FileMaker contain years of CRM history that should be queryable through Dent Brain alongside evidence from Dropbox, Granola, and Gmail. Phase 5 (Dropbox import) gets a sibling: **Phase 5b — FM Notes import**. Each FM note becomes one evidence record with `source: filemaker:notes:<note-id>` and `author: <FM author field>`. Same classification, quarantine, and rebuild path as Dropbox import.

This is one-time. After import, FM Notes continue to be Steve's quick-capture in FM, and we add a v1 daily delta job to pick up new ones. Not in MVP.

### Open federation questions (must resolve in Phase 0.5)

1. **Which FM MCP is Steve using?** Vendor-provided (Claudemcp.com or similar)? Custom? FileMaker Cloud's own? The integration depth depends.
2. **What read operations does it expose?** ID lookup is minimum. Search, filter, related-record traversal would unlock the v1 use cases (e.g., "find people with tag X").
3. **Multi-user access.** Can the same MCP serve all 6 team members with their own credentials, or is it scoped to Steve? If single-user, MVP needs a workaround (e.g., service account).
4. **Permissions.** Does FM enforce per-user access, or does the MCP connection get blanket access?
5. **Latency / rate limits.** Does a `/sales-check` query that hits FM 5x feel snappy or sluggish?
6. **FM Note schema.** What fields are on `Notes Q` and `Sticky Notes`? Need this for the import classifier.

Phase 0.5 is a discovery + spike phase to answer these. ~1 day of work with Steve in the room.

## Canonical Use Cases (new in v0.9)

These are the queries Steve and the team actually want to make. They define the product. **Use case 3 is fully MVP-deliverable**; the others are v1+ but the architecture must not preclude them.

### Use case 1: "What did we tell [attendee] about carrying forward registration?"
- **Shape:** point lookup against a specific person, scoped to a topic (registration policy).
- **Data sources:** FM `Communication Items` (outbound emails) + FM `Notes Q` (CRM notes) + Dent Brain evidence (email ingest, meeting notes, `/append-evidence`).
- **What unlocks it:** federated entity page + skill `/recall <person> <topic>` that filters across FM comms log and Dent Brain evidence by topic keyword. **Status: v1 (after Gmail ingest), not MVP.** MVP can do a manual version: search Dent Brain + open the FM record.
- **Note:** "Almost all cases are individual and not policy-based" — this means we should NOT try to extract a "registration policy" entity. The answer lives in the per-person comms history.

### Use case 2: "Two paragraphs about Dent community members relevant to someone in Xbox at Microsoft"
- **Shape:** filter People by tags / company / role, then surface recent activity, then write two paragraphs.
- **Data sources:** FM `Tags People` (who has tags like "gaming", "Xbox", "Microsoft alum"), FM `People` (current employer, role) + Dent Brain evidence about recent updates ("Sarah just joined Halo team — see meeting note from 4/12").
- **What unlocks it:** federation alone. Claude in Cowork can call FM MCP for tag search, call Dent Brain for recent evidence on each match, and write the two paragraphs. No bespoke skill needed. **Status: fully MVP, conditional on FM MCP supporting tag search.**
- **This is the killer use case for fundraising / recruiting / outreach.** A `/community-match` skill in v1 is a convenience wrapper that pre-bundles the prompt — capability is already there in MVP.

### Use case 3: "Summarize the state of the Dent:Blend Austin project"
- **Shape:** entity-page query for a project, materialized from meeting + email evidence.
- **Data sources:** Dent Brain evidence (meeting notes, emails, observations) referencing `entities/projects/dent-blend-austin`.
- **What unlocks it:** the MVP itself. `get_page(entities/projects/dent-blend-austin)` returns the compiled entity page with confirmed facts, working inferences, open questions, evidence timeline. **Status: fully MVP.**
- **This is the use case Steve should test in week 1.** It's the cleanest validation of the materializer's value.

### Use case 4: "One of our Denters is in a Hollywood TV series — who should I introduce them to?"
- **Shape:** filter People by Hollywood / TV / film tags, surface their recent context, let Claude rank fit. NOT a social-graph traversal — just "find the right matches."
- **Data sources:** FM `Tags People` (industry tags) + FM `People` (employer, role) + Dent Brain evidence about who's been talking about Hollywood, who has TV experience, who might mentor.
- **What unlocks it:** federation alone. Claude calls FM MCP for tag search ("Hollywood", "TV", "film", "entertainment"), calls Dent Brain for recent context on each match, returns ranked candidates with reasoning. **Status: fully MVP, conditional on FM MCP supporting tag search.**

### Use case 5: "Initial invite list for our San Diego Comic Con reception"
- **Shape:** compound filter on People — location (SoCal / San Diego), tags (comics, gaming, entertainment), past attendance at related events. Output is a list with names, emails, and a one-line "why."
- **Data sources:** FM `People` (location), `Tags People` (interest tags), `Past Registrations` / `Past Conf People` (event history). Dent Brain layer adds "who's been mentioned in recent meetings about SDCC or related topics."
- **What unlocks it:** federation alone. Claude calls FM MCP with compound filter, joins against Dent Brain evidence for freshness, returns the list. **Status: fully MVP, conditional on FM MCP supporting compound filters across People + Tags + Past Registrations.**

### What these use cases tell us

- **Federation IS the intelligence layer.** With FM MCP + Dent Brain MCP both installed in Cowork, Claude orchestrates them naturally for UC2, UC3, UC4, UC5. Bespoke skills (`/community-match`, `/who-knows-whom`, `/invite-list`) become **convenience wrappers** that pre-bundle prompts and improve UX, not capability adds.
- **The hybrid is the product.** None of the high-value use cases are pure-Dent-Brain or pure-FileMaker. They all need both layers.
- **Tags + filters from FM are load-bearing.** UC2, UC4, UC5 lean on FM's tag taxonomy and compound filters. **If the FM MCP only supports ID lookup, these use cases collapse back to v1.** Phase 0.5 must verify FM search/filter capability or this whole expansion regresses.
- **UC3 is the safety net.** If FM federation underwhelms, UC3 (Dent:Blend Austin status) alone justifies MVP. It's pure Dent Brain.
- **UC1 is partial-MVP.** FM-only path works (FM Comm Items + FM Notes); Gmail-bridged path needs Gmail ingest, which is v1.
- **Intelligence skills become v1 convenience layer, not v1 capability layer.** They wrap proven patterns from MVP. Priority: pre-bundle the prompts users find themselves writing repeatedly.

## MVP Scope (concrete)

### IN (ship to Steve)

**Infrastructure**
- Railway deployment of dent-brain server (Bun) + Supabase (Postgres + pgvector).
- Custom subdomain `dent-brain.dentthefuture.com/mcp` with bearer auth.
- Audit log on every MCP tool call.

**Data**
- Evidence log schema per v0.7 §6 (id, source, author, timestamp, ingested_at, content, content_hash, entity_refs[], stream_id, batch_id).
- `dent-brain-data` private repo in dentthefuture GitHub org, initialized with namespace scaffolding per v0.7 §7 and `DENT_SCHEMA.md`.
- Seed entity pages for Steve, Jason, Dent itself (hand-written, to anchor entity detection).

**MCP tools (server-side, exposed by Dent Brain)**
- `append_evidence(entity_refs, content, source_context?)`
- `get_evidence(entity_slug, limit?)`
- `get_page(slug)` — entity or namespace, renders compiled sections (confirmed facts, working inferences, open questions, conflicts, evidence timeline). For person entities, includes a `filemaker_record_id` pointer in frontmatter when one is linked.
- `search(query)` — gstack's existing hybrid RRF over evidence + entity pages
- `list_recent_writes(since, user?)`
- `whoami()`
- `rebuild_entity(slug)` — rebuilds the whole compiled page from evidence: runs synthesis, writes markdown, updates search index. Does NOT call FM at rebuild time.
- `flag_fact(entity_slug, claim, reason?)` — marks a synthesized claim as wrong; demotes it on next rebuild and writes to the correction log
- `get_provenance(entity_slug)` — lists all sources and authors that contributed to a page, for "where did this come from?" queries
- `link_filemaker(entity_slug, fm_record_id, fm_table)` — associates a Dent Brain entity with a FileMaker record. Persists in entity frontmatter. Used by importers and `/append-evidence` when entity detection finds an FM match.

**FileMaker MCP (separate connector, installed alongside Dent Brain)**
- Whatever Steve's existing connector exposes (Phase 0.5 discovery resolves this).
- Both connectors are installed in each user's Cowork. Skills can call either or both.
- Dent Brain's server does NOT proxy to FileMaker. Federation happens at the Claude / skill layer, not at the server layer. This keeps Dent Brain's server stateless w.r.t. FM and avoids credential-handling.

**Materializer (LLM-driven, MVP-grade)**
- Renders compiled sections: confirmed facts, working inferences, open questions, conflicts, evidence timeline.
- **Mandatory source-tag backlinks on every synthesized claim.** No bare prose. Pattern: `Interested in speaking at Dent 2026. [src: jason-paste:2026-04-14, jeff-paste:2026-04-15]`.
- Conflict detection is mechanical when possible: evidence records with opposing claims (e.g., "travel-constrained" vs "not travel-constrained") about the same entity go to the Conflicts section until resolved.
- Runs on `append_evidence` (enqueues a rebuild) and on-demand via `rebuild_entity`.
- Correction log captures every `flag_fact` call; weekly review drives prompt iteration.

**Ingest**
- `/ingest-dropbox-tree` — bulk import with classification, staged batches, `quarantine_batch` + `diff_entity` tooling for review.
- `/append-evidence` skill — user-invoked or signal-detector-suggested, available in Cowork.
- `/flag-fact <entity> <claim>` skill — Steve's primary mechanism for correcting hallucinated facts. One-click in Cowork.

**Proactive UX (new, this session)**
- `signal-detector-dent` — per-message skill in Cowork plugin. Reads active session context, matches against Dent entities (seed pages + entities discovered during Dropbox import), sponsor companies, conference phrases, dent-related email/domain patterns. When matched and confidence > threshold, suggests one of:
  - "I see you're analyzing Dent social media ad performance. Want me to `/append-evidence` about the effectiveness?"
  - "I see you're drafting a sponsorship PDF for {company}. Want me to `/append-evidence` about who it's being sent to?"
  - "I see you mentioned {speaker} and they're in the Dent speaker pipeline. Want me to `/append-evidence` about this conversation?"
- Rate-limit suggestions to ≤2 per session. One-click dismiss. User can `/signal-detector-dent off` to silence for a session.

**Install**
- Cowork plugin bundle: connector URL for Dent Brain MCP + connector URL for FileMaker MCP (Steve's pattern, generalized for the team), skills bundle (`/append-evidence`, `/flag-fact`, `whoami`, `signal-detector-dent`), install walkthrough doc.
- Admin CLI for issuing per-user bearer tokens (Dent Brain side).
- FM MCP install instructions for each team member (depends on Phase 0.5 discovery).
- Onboarding DM template for non-technical users.

**Steve onboarding**
- Admin token issued.
- Install walkthrough with Jason present (video call, one shot).
- First week: Steve uses it for real Dent work, logs friction in a shared doc.

### OUT of MVP (deferred to v1 and v1.1)

- **Mechanical confirmed-facts extraction** (structured claim extraction + ≥2-source corroboration). Post-MVP hardening, driven by correction-log data.
- **FM Notes import** (Phase 5b) is OUT for v0 ship-to-Steve. Lands in first v1 sprint after Steve validates the basic shape. Reasoning: MVP needs to prove federation works at all before importing years of FM Notes into evidence.
- **FM daily delta job** (picking up new FM Notes after import). v1.1.
- **Two-way write to FileMaker.** v2 conversation. MVP and v1 are read-only against FM.
- Server-side Dropbox drop folder cron (MVP has one-time bulk import only).
- Gmail scheduled ingest + Granola ingest. First v1 addition after Steve validates MVP.
- RSS streams (Jason X, Steve LinkedIn, Dent blog).
- **Intelligence skills as convenience wrappers** for common federation patterns: `/recall <person> <topic>`, `/community-match <prospect>`, `/who-knows-whom <topic>`, `/invite-list <event>`, `/sales-check <person>`, `/prep-speaker <name>`, `/session-plan`, `/dent-library`, `/dent-status`, `/evaluate-session`, `/marketing-brief`. All v1+. **Capability is in MVP via federation; the skills make it ergonomic and shareable.** Priority order in v1 driven by which patterns Steve writes by hand most often.
- Dream cycle / nightly enrichment.
- Git archive snapshot job (v1 after MVP; not transactional in any case).
- ACLs (v1.1 per v0.7).
- Scraper webhooks, MailerLite, Google Drive, Slack archive.

## Open Questions

1. **FileMaker MCP shape (BLOCKING — Phase 0.5).** Which connector? What ops? Multi-user vs single-user? Permissions? Latency? FM Notes schema? See FileMaker Federation §"Open federation questions."
2. **Entity-to-FM linking heuristic.** When `/append-evidence` mentions "Mike Cottmeyer," do we (a) auto-link to FM record by name+email match, (b) suggest a link and let user confirm, (c) leave unlinked and let an enrichment pass connect later? MVP default: (b) — surface candidates, ask user once, persist the link.
3. **Signal-detector trigger list.** What exactly counts as a Dent signal in a Cowork session? Seed from DENT_SCHEMA.md + imported entities + FM People + FM Tags, but needs tuning with Steve.
4. **Dropbox classification accuracy.** v0.7 §17 sets <20% human-correction target. MVP should measure this on the staged import and block ship-to-Steve if classification is clearly broken.
5. **Materializer cost budget.** LLM synthesis on every entity rebuild has non-trivial token cost, especially as evidence density grows. Target: materializer re-run cost for a heavy entity (200+ evidence records) under $0.10 per rebuild. If it exceeds that, implement incremental synthesis (only new evidence since last rebuild) before shipping.
6. **Hallucination rate calibration.** Track Steve's `/flag-fact` rate from day one. If >5 flags per 100 claims by end of week 1, accelerate the mechanical-corroboration hardening plan.
7. **`/append-evidence` free-text vs structured claims.** Accepting free text for MVP is fine. When mechanical-corroboration hardening starts (post-MVP), revisit.
8. **Entity detection on import.** Imported files must create entity pages for people/companies/sessions not yet seeded. Heuristic: any name appearing in ≥3 files or any @dentthefuture.com or known-partner email becomes an entity. Cross-reference with FM People before creating to avoid duplicate entities.

## Success Criteria (MVP specifically)

MVP is successful if, 2 weeks after ship-to-Steve, all of these are true:

**Adoption**
1. Steve opens Cowork at least 3 times per week and interacts with Dent Brain.
2. Steve has triggered `/append-evidence` (via signal-detector suggestion or direct invoke) at least 10 times across the two weeks.
3. Steve has queried the brain (search or entity page read) at least 20 times.
4. **Steve has run at least 3 of the 5 canonical use cases successfully and reported each useful.** Required: UC3. Strong recommended: UC2, UC4, UC5 (assumes FM MCP capability confirmed in Phase 0.5).
5. **Federation in action:** at least one query Steve runs touches both MCPs (Dent Brain + FileMaker) in a single Cowork turn.

**Correctness**
6. >90% of Steve's `/append-evidence` calls land on the correct entity page (no missing entity_ref, no wrong entity).
7. Dropbox import produced entity pages for the top 20 expected entities (Jason, Steve, Jeff, Robin, Andreas, Morgan, Dent, and ~13 known speakers/sponsors).
8. Signal-detector suggestions: >50% accepted or ignored-without-annoyance, <50% dismissed as noise. Steve reports qualitatively whether the pattern helps or hurts.
9. **Hallucination rate tolerable.** `/flag-fact` calls by Steve < 5 per 100 synthesized claims read. Above that threshold, accelerate mechanical-corroboration hardening.
10. **Every synthesized claim on every entity page has at least one source-tag backlink.** Zero tolerance for bare prose in compiled sections.
11. `rebuild_entity` is reproducible enough that a second rebuild on unchanged evidence produces substantively identical compiled sections (exact prose may differ; facts and inferences must not). Formal determinism is the post-MVP mechanical rubric's job.
12. Zero silent data loss: every evidence record appended is retrievable; every `/append-evidence` call either succeeds with an ID returned or fails with an explicit error.
13. **Federation links:** at least 10 person entity pages have a confirmed `filemaker_record_id`. Steve can ask "what's Mike's company?" and get a correct answer from FM via federation.

**Hygiene**
14. Steve can complete the install in under 20 minutes with zero terminal (extra 5 min for FM MCP).
15. Jason has not had to write code to fix Steve's environment once setup is done.
16. At least one Steve quote worth quoting (good or bad) at the end of week 2.

- Gate: `get_page(entities/people/steve-broback)` returns the hand-written page.

**Phase 3 — Materializer (LLM synthesis with guardrails)**
- Synthesis prompt produces confirmed facts, working inferences, open questions, conflicts, evidence timeline.
- **Mandatory source-tag backlinks** on every synthesized claim. Reject materializer output that fails this check; re-prompt until compliant.
- Conflict detection: mechanical scan for opposing claims + LLM pass for semantic contradictions.
- `rebuild_entity` implements synthesis. Queued automatically on `append_evidence`.
- Correction log table: `flag_fact` writes `(entity, claim, reason, user, timestamp)` for weekly review.
- Unit tests: every synthesized claim has ≥1 source backlink; flagged claims are demoted on rebuild; rebuild is idempotent on unchanged evidence (substantive-equivalence, not byte-identity).
- Gate: Jason injects 20 test evidence records across 3 entities, runs `rebuild_entity`, inspects synthesized pages, flags any bad facts, sees them demoted on next rebuild.

**Phase 4 — `/append-evidence`, `/flag-fact`, FM linking**
- `/append-evidence`: entity-detection pass on free-text input; match against seed entities + any entities created so far; prompt to create new entity page if unknown; writes evidence record, queues rebuild.
- **FM linking pass:** when entity detection finds a person, query FM People for name+email match. If found, surface candidate to user ("Looks like Mike Cottmeyer = FM record #4521. Link?"). On confirm, call `link_filemaker(entity_slug, fm_id, "People")`.
- `/flag-fact`: accepts entity + claim (or claim substring), writes to correction log, triggers rebuild.
- Gate: Jason appends 5 evidence records, sees compiled pages update; flags one bad fact, sees it demoted; at least 3 entities have a confirmed FM link in their frontmatter.

**Phase 5 — Dropbox bulk import**
- `/ingest-dropbox-tree` CLI with classification, staged batches, quarantine.
- Dry-run mode: reports classifications without writing.
- Dry-run on a small subtree (2025 meeting notes); review with Jason; tune classifier.
- Staged import of progressively larger subtrees. Quarantine + fix loop until classification <20% human-correction rate.
- **Entity creation cross-references FM People** before creating new entity pages — name+email lookup against FM, and when matched, the new entity page is created with `filemaker_record_id` already populated.
- Full import with Jason review. All affected entities rebuilt.
- Gate: top 20 expected entities have non-empty compiled pages built from real Dropbox content; ≥10 of them are FM-linked.

**Phase 5b — FM Notes import (DEFERRED to v1, listed here for visibility)**
