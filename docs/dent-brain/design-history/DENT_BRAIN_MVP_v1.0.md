## Eng-Review Decisions (added 2026-04-21)

Architectural and implementation decisions made during /plan-eng-review. These are binding for the build phase.

### Architecture

**A1. Materializer concurrency: debounce per entity, 30s window.** Use `pg-boss` (Postgres-native job queue, Layer 1). Schedule rebuild with entity-slug as dedup key; new `append_evidence` on the same entity within 30s resets the timer. One rebuild per burst. No Redis, no custom queue.

**A2. Evidence schema: GIN index on `entity_refs`.** `CREATE INDEX evidence_entity_refs_gin ON evidence USING GIN (entity_refs)`. Non-negotiable for query performance.

**A3. Audit log fields spec.** Every MCP call writes: `(timestamp, user_id, tool_name, args_redacted, result_code, latency_ms, session_id, cost_usd)`. Bearer tokens and PII redacted from args. Cost included for materializer and LLM-classifier calls.

**A4. Plugin update mechanism.** Ship `/update-dent-brain` convenience skill that re-fetches the plugin bundle from `jasonp/dent-brain` at a pinned version. Document in `INSTALL.md`.

**A5. Entity disambiguation: name-first with FM escalation.** Name-based matching is the default. Escalation rule: if FM contains 2+ People records with identical `Full_Name` but different `PK_People_ID`, require email match from observation context. If no email available, flag for Steve manual resolve via `/resolve-entity` skill. Secondary emails per FM person are handled — email is a lookup key, `PK_People_ID` is identity.

**A6. Signal-detector feasibility spike in Phase 0.** 1-hour test: install a dummy skill in a throwaway Cowork session, verify it can read every user message (not just invoked skills). Document in `FILEMAKER_FEDERATION.md`. If per-message hook is unsupported, reshape Phase 6 as a session-start digest or keyword-flag skill. Do NOT discover this mid-Phase 6.

**A7. Plugin install path verification spike in Phase 0** (broadened per cross-model review). Install Dent Brain + FM MCPs in a throwaway Cowork session. Verify: per-user tokens work (not shared), bundled skills discoverable across connectors, no MCP name collisions, auth flow clean. Document in `FILEMAKER_FEDERATION.md`. This de-risks Phase 7.

**A8. Prompt versioning.** Semver'd prompt templates stored in Postgres (`materializer_prompts` table). Every synthesized page stamped with `prompt_version` in frontmatter. `rebuild_entity --older-than-prompt vN` sweeps pages to bring them current. Correction log groups findings by prompt version for tuning.

**A9. FM-Dent Brain conflict resolution: FM wins, with staleness surfacing.** Materializer prompt gets a "contradict-FM" rule: FM is authoritative for owned fields (name, email, current employer, registrations, payments, tags). If Dent Brain evidence is newer than FM's `ModificationTimestamp` AND conflicts with FM, surface both and flag as `may contradict FM — last meeting note suggests X; FM says Y (updated Z)`. Steve manually updates FM when the conflict is real staleness.

**A10. Materializer rollback via last-good snapshots.** Before each rebuild, copy current entity page markdown to `entity_snapshots` table. Keep last 5 versions per entity. `rebuild_entity --revert <slug>` restores prior. Combined with A8 prompt versioning, provides both entity-level revert and project-wide prompt pin.

### Code Quality

**CQ1. Entity detection as a standalone service.** Single module `src/entity-detection/` with one public API: `detectEntities(text, context) → {matches: [{slug, fm_id, confidence, rule}], unknowns: [string]}`. Used by `/append-evidence`, Dropbox importer, and FM-linking pass. No duplication.

**CQ2. Materializer structural validator (CRITICAL).** Every synthesized claim under `## Confirmed facts`, `## Working inferences`, `## Open questions` must match `[src: ...]` regex. Malformed output is rejected; re-prompt up to 3 times. On 3rd failure, fall back to timeline-only page with `materializer_failed: true` flag. Non-negotiable test coverage.

**CQ3. `/flag-fact` fuzzy matching.** Match attempts in order: exact → substring → embedding similarity (>0.8). Log match mode in correction log so tuning can see which mode was used. Non-match UX: "couldn't find that claim, did you mean X or Y?"

**CQ4. FM MCP client wrapper.** All FM calls from Dent Brain skills go through `src/federation/fm-client.ts` — logs latency, errors, call counts per session. Required for P1 performance monitoring.

**CQ5. Error taxonomy documented in Phase 1.** Minimum set: `EVIDENCE_NOT_FOUND`, `EVIDENCE_ENTITY_UNKNOWN`, `ENTITY_NOT_FOUND`, `AUTH_INVALID`, `FM_UNREACHABLE`, `MATERIALIZER_FAILED`, `RATE_LIMITED`. Write to `docs/ERROR_TAXONOMY.md` in dent-brain-data repo.

**CQ6. Classifier strategy: rules-first with LLM fallback.** Filename + folder location rules catch ~80% of files. Unmatched files → Claude classification call. Classifier output always includes the rule that matched (or "llm-fallback"), making tuning debuggable.

**CQ7. Materializer cost: full rebuild in MVP, watchdog at $50/week.** Simple is right for one user. Track per-rebuild cost in `audit_log.cost_usd`. Weekly rollup with Slack alert if crossed. Build incremental synthesis in v1 only if alert fires.

### Performance

**P1. FM fan-out cache (conditional).** If Phase 0.5 latency timing reveals >5s on UC2/UC4 fan-out queries, add session-scoped in-memory cache keyed by `(fm_table, fm_record_id)`, 60s TTL. Not MVP unless needed.

**P2. Signal-detector hot path.** Signal-detector fetches trigger list (entity names + FM tags + DENT_SCHEMA triggers) once per session into local cache. Server endpoint returns versioned list; client checks version on session start only. Never per-message.

**P3. Git archive (v1): only-changed-entities filter.** When git archive lands in v1, filter commits to entities modified since last snapshot. Avoid empty commits.

## Problem Statement

v0.7 is architecturally sound but sized for an 11-phase build before any team member touches the system. Steve Broback is available to alpha now. The primary risk identified in this office-hours session is **team adoption**, not architecture — the plan needs to get a real user doing real work as fast as possible, not build nine phases of machinery speculatively. MVP v0.8 keeps the core value prop of v0.7 (compiled entity pages with typed sections, not raw timelines) and cuts the parts that don't need to exist before Steve validates the shape: stream ingestors, intelligence skills, dream-cycle, server-side Dropbox cron, Gmail scheduled ingest, Granola ingest.

**On hallucination risk:** LLM-synthesized compiled-truth sections are kept in MVP. The alternative — timeline-only pages — ships a log, not a brain. Compiled truth is the token-efficient surface that makes day-to-day queries ("did we pitch Mike?") fast and useful. The risk of hallucinated confirmed facts is accepted for MVP with guardrails: mandatory source-tag backlinks on every synthesized claim, `/flag-fact` skill for fast correction, and a correction log that drives prompt iteration. The mechanical corroboration rubric discussed in this session (structured claims corroborated by ≥2 evidence records) remains the post-MVP hardening path — we tighten the authority surface once Steve has flagged enough bad facts to give us a calibration signal.

## Premises

These are the load-bearing assumptions. Each was challenged in this office hours session.

1. **The evidence-log-first architecture from v0.7 is correct.** Append-only evidence records with typed entity views solve the multi-writer, imports-blow-up-mutable-designs, compiled-truth-hides-uncertainty problems. Agreed.

2. **Compiled truth ships in MVP with guardrails; mechanical hardening comes later.** The token-efficiency and day-to-day utility of compiled entity pages is too valuable to defer. MVP uses LLM synthesis for confirmed facts, working inferences, and conflict detection. Guardrails: every synthesized claim carries source-tag backlinks, `/flag-fact` enables one-click correction, and a correction log drives prompt iteration. Post-MVP hardening path: migrate confirmed-facts to mechanical extraction (structured claims corroborated by ≥2 evidence records, no LLM prose in the authority surface) once correction-log data tells us where the prompts fail. Revised this session after pushback.

3. **Steve is enough to validate MVP.** One real user doing real Dent work is worth more than 11 phases of machinery. If Steve uses it and wants Jeff on it, we expand. If Steve bounces off it, we learn why before building more. Agreed.

4. **Proactive `/append-evidence` suggestion is core, not optional.** Asking users to remember to invoke a skill is a losing pattern. The signal-detector skill that reads Cowork session context and suggests the append is the actual UX. Added this session.

5. **Materializer synthesis is in MVP.** Confirmed facts, working inferences, open questions, conflicts, and timeline all ship in MVP. Synthesis is LLM-driven. Guardrails enumerated in premise 2. Hallucination risk is accepted and Steve is the primary detector via `/flag-fact`. Revised this session.

6. **Bulk Dropbox import must happen before MVP ships to Steve.** An empty brain is not testable. The import is also the first real stress-test of classification and entity detection. Agreed.

## Approaches Considered

### Approach A: Ship v0.7 as written, with corrections
Push through all 11 phases before first user contact. Correct the confirmed-facts synthesis mechanism along the way.
- Pros: complete system at end.
- Cons: ~3 months of dark work before Jeff/Steve touch anything. High risk that the shape is wrong for actual Dent workflow. Signal-detector pattern not in scope until very late.

### Approach B: Ship narrowest useful wedge to Steve (RECOMMENDED, revised)
Evidence log + LLM-synthesized compiled entity pages (confirmed facts, inferences, open questions, conflicts, timeline) + Dropbox bulk import + signal-detector + `/append-evidence` + `/flag-fact` + non-technical install. No streams, no intelligence skills, no dream cycle, no server-side cron ingest. Steve on it in ~3-4 focused build weeks.
- Pros: real user validates real behavior on the actual product (compiled brain, not a log). Signal-detector ships as core MVP UX. Correction log from `/flag-fact` directly drives the post-MVP mechanical-corroboration hardening.
- Cons: hallucination risk in confirmed-facts is accepted, mitigated by source-tag backlinks + `/flag-fact`. Materializer cost needs monitoring as evidence density grows. Dropbox classification quality is still the primary ingest-failure surface.

### Approach C: Notion/Airtable substrate
Skip custom evidence log entirely. Use Notion as the data layer; skills read/write Notion API.
- Pros: fastest to ship. Free UI for team.
- Cons: kills gstack-substrate thesis and portability story. Tied to Notion's performance ceiling. Migration cost later is high. Not interesting to build.

## Recommended Approach: B

**Why:** v0.7's architecture is right. The risk isn't architectural, it's adoption and ingest-quality. Approach B puts both in front of Steve as fast as possible while shipping the actual value prop (compiled entity pages, not a log). v0.7's typed-sections design is preserved in MVP; the change is that LLM synthesis runs the sections instead of mechanical rules. Mechanical rules become a v1 hardening pass driven by `/flag-fact` data. Nothing in MVP v0.8 contradicts v0.7's long-term targets.

### The federation pattern (lazy reads, not import)

We do NOT import FileMaker into Dent Brain. Importing creates a stale-cache problem: registrations, payments, and tags change in FM constantly with no reverse-flow.

Instead:
- **Each Dent Brain user installs both MCP connectors in Cowork**: Dent Brain (this project) + FileMaker (Steve's existing connection, made shareable). Skills and intelligence agents call both.
- **Entity pages reference FM IDs.** A person entity page header includes `filemaker: { record_id: 12345, layout: "People" }`. Skills resolve that pointer against FM at query time.
- **Materializer does NOT inline FM data on every rebuild.** Reasons: (a) FM data changes between rebuilds and inlining creates staleness, (b) materializer cost stays bounded, (c) FM rate limits / latency don't block evidence rebuilds. Instead, the materializer leaves a "linked record" pointer.
- **Read-time enrichment.** When a skill answers a query about a person ("what's Mike's company?"), it fetches the FM record live, combines with Dent Brain's evidence-derived sections, and answers. The user sees one merged view.
- **MVP: read-only against FM.** Even though writes are verified working, Dent Brain does not write to FM in MVP. Reasoning: we expanded MVP scope significantly in v0.9 (1 use case → 4); adding writes on top risks overloading Steve's alpha. Capability is verified and ready for v1.

### Write boundary decision (revisit in v1)

**v1.0 MVP: read-only.** No Dent Brain writes to any FM layout. Evidence stays in Dent Brain's Postgres + markdown; FM stays untouched except by its normal human + integration workflows.

**v1 will reconsider, with these specific write patterns on the table:**
1. **Promote-to-FM-People.** When Dent Brain discovers a new person (via Dropbox import, `/append-evidence`, or email ingest) who isn't in FM, offer a one-click "promote to FM People" action. Creates FM People record with name, email, source, Dent Brain entity backlink. Write-behind-confirmation (never automatic).
2. **Observation scratchpad layout.** Dent-Brain-owned FM layout (e.g., `DB_Observations`) where Dent Brain writes observations keyed to a Person record. Makes Dent Brain observations visible to team members who live in FileMaker Pro instead of Cowork. Never writes to core layouts (People, Event Registration, Purchases).
3. **Sticky Notes parity.** If Steve wants, Dent Brain could write to `Sticky Notes` in parallel with its own evidence log so observations appear in his native FM workflow.

**Not in scope in any version:**
- Writes to `People` core fields (name, email, phone, address) — too high-risk.
- Writes to `Event Registration`, `Past Registrations`, `HR Purchases`, `RHR Purchases` — financial data, FM-only.
- Writes to integration-source layouts (MailChimp, GetProspect, JoinIt, Regfox) — external sources of truth.

### Loop prevention

If future FM Notes import (Phase 5b, v1) ingests `Notes Q` / `Sticky Notes` into Dent Brain evidence, AND future Dent Brain writes observations back to FM (option 3 above), we must prevent round-trip loops. Marker: records authored by `CreatedBy = mcp_claude` are skipped by the FM Notes ingest. Audit trail already populates this field correctly.

### Historical FM Notes import (one-time, into evidence log)

`Notes Q` and `Sticky Notes` in FileMaker contain years of CRM history that should be queryable through Dent Brain alongside evidence from Dropbox, Granola, and Gmail. Phase 5 (Dropbox import) gets a sibling: **Phase 5b — FM Notes import**. Each FM note becomes one evidence record with `source: filemaker:notes:<note-id>` and `author: <FM author field>`. Same classification, quarantine, and rebuild path as Dropbox import.

This is one-time. After import, FM Notes continue to be Steve's quick-capture in FM, and we add a v1 daily delta job to pick up new ones. Not in MVP.

## Canonical Use Cases (new in v0.9)

These are the queries Steve and the team actually want to make. They define the product. **Use case 3 is fully MVP-deliverable**; the others are v1+ but the architecture must not preclude them.

### Use case 1: "What did we tell [attendee] about carrying forward registration?"
- **Shape:** point lookup against a specific person, scoped to a topic (registration policy).
- **Data sources:** FM `Communication Items` (outbound emails) + FM `Notes Q` (CRM notes) + Dent Brain evidence (email ingest, meeting notes, `/append-evidence`).
- **What unlocks it:** federated entity page + skill `/recall <person> <topic>` that filters across FM comms log and Dent Brain evidence by topic keyword. **Status: v1 (after Gmail ingest), not MVP.** MVP can do a manual version: search Dent Brain + open the FM record.
- **Note:** "Almost all cases are individual and not policy-based" — this means we should NOT try to extract a "registration policy" entity. The answer lives in the per-person comms history.

### Use case 2: "Two paragraphs about Dent community members relevant to someone in Xbox at Microsoft"
- **Shape:** filter People by tags / company / role, then surface recent activity, then write two paragraphs.
- **Data sources:** FM `Tags People` (who has tags like "gaming", "Xbox", "Microsoft alum"), FM `People` (current employer, role) + Dent Brain evidence about recent updates ("Sarah just joined Halo team — see meeting note from 4/12").
- **What unlocks it:** federation alone. Claude in Cowork can call FM MCP for tag search, call Dent Brain for recent evidence on each match, and write the two paragraphs. No bespoke skill needed. **Status: fully MVP-deliverable (FM MCP tag search confirmed working).**
- **This is the killer use case for fundraising / recruiting / outreach.** A `/community-match` skill in v1 is a convenience wrapper that pre-bundles the prompt — capability is already there in MVP.

### Use case 3: "Summarize the state of the Dent:Blend Austin project"
- **Shape:** entity-page query for a project, materialized from meeting + email evidence.
- **Data sources:** Dent Brain evidence (meeting notes, emails, observations) referencing `entities/projects/dent-blend-austin`.
- **What unlocks it:** the MVP itself. `get_page(entities/projects/dent-blend-austin)` returns the compiled entity page with confirmed facts, working inferences, open questions, evidence timeline. **Status: fully MVP.**
- **This is the use case Steve should test in week 1.** It's the cleanest validation of the materializer's value.

### Use case 4: "One of our Denters is in a Hollywood TV series — who should I introduce them to?"
- **Shape:** filter People by Hollywood / TV / film tags, surface their recent context, let Claude rank fit. NOT a social-graph traversal — just "find the right matches."
- **Data sources:** FM `Tags People` (industry tags) + FM `People` (employer, role) + Dent Brain evidence about who's been talking about Hollywood, who has TV experience, who might mentor.
- **What unlocks it:** federation alone. Claude calls FM MCP for tag search ("Hollywood", "TV", "film", "entertainment"), calls Dent Brain for recent context on each match, returns ranked candidates with reasoning. **Status: fully MVP-deliverable (FM MCP tag search confirmed).**

### Use case 5: "Initial invite list for our San Diego Comic Con reception"
- **Shape:** compound filter on People — location (SoCal / San Diego), tags (comics, gaming, entertainment), past attendance at related events. Output is a list with names, emails, and a one-line "why."
- **Data sources:** FM `People` (location), `Tags People` (interest tags), `Past Registrations` / `Past Conf People` (event history). Dent Brain layer adds "who's been mentioned in recent meetings about SDCC or related topics."
- **What unlocks it:** federation alone. Claude calls FM MCP with compound filter, joins against Dent Brain evidence for freshness, returns the list. **Status: fully MVP-deliverable (FM compound find confirmed across People + Tags + Past Registrations layouts).**

### What these use cases tell us

- **Federation IS the intelligence layer.** With FM MCP + Dent Brain MCP both installed in Cowork, Claude orchestrates them naturally for UC2, UC3, UC4, UC5. Bespoke skills (`/community-match`, `/who-knows-whom`, `/invite-list`) become **convenience wrappers** that pre-bundle prompts and improve UX, not capability adds.
- **The hybrid is the product.** None of the high-value use cases are pure-Dent-Brain or pure-FileMaker. They all need both layers.
