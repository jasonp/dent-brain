# v0.40.0.0 — Upstream sync (gbrain v0.30.1 → v0.37.9.0)

## What changed

- **65 upstream commits merged** into the fork in one reviewed wave. New
  capabilities: ZeroEntropy `zembed-1` + `zerank-2` reranker, skillpack
  registry, Cathedral III code-intelligence MCP ops (`find_trajectory`,
  `code_callers`/`callees`/`def`/`refs`, `code_blast`/`code_flow`), hindsight
  calibration, cross-modal `search_by_image`, hot-memory fact extraction.
- **~76 new schema migrations** (schema version 1 → 80). These apply
  automatically the next time you run `dbrain` (the `postinstall` hook calls
  `dbrain apply-migrations --yes`, and every command path applies pending
  migrations on connect).
- **`OperationContext.sourceId` is now required** at the type level, auto-filled
  `'default'` by every transport. Read-side op handlers route source scope
  through `sourceScopeOpts` — a P0 leak seal so an authenticated multi-source
  query can't surface another source's data in rankings. Single-source brains
  see no behavior change.

## Will my brain work worse if I do nothing?

**No, for the default path.** Schema migrations apply on their own. The
ZeroEntropy reranker is **off** on the `balanced` and `conservative` search
modes (the defaults) — search behaves exactly as it did on v0.39. The reranker
only engages when you opt into `tokenmax` mode.

## Optional: turn on ZeroEntropy reranking

If you want `zerank-2` reranking on retrieval:

1. Get a key from ZeroEntropy and export it: `export ZEROENTROPY_API_KEY=...`
2. Set search mode to tokenmax: `dbrain search modes --set tokenmax`

If you set `tokenmax` without a key, the reranker degrades gracefully (the
pipeline skips the rerank stage rather than erroring) — but set the key to get
the benefit.

## For maintainers: cleaner future syncs

This merge hit 106 conflicts, 50 of them `add/add` — entire subsystems
(`eval-contradictions/`, `facts/`) that a prior **squashed** sync commit had
severed from their upstream ancestry. git saw two unrelated files where there
was one lineage, so it couldn't auto-merge. To avoid this next time, run upstream
syncs through `bun run sync:upstream` and prefer a real merge commit (not a
squash) so ancestry is preserved and the next sync three-way-merges cleanly.
