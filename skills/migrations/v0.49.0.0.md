# v0.49.0.0 Migration: off ZeroEntropy before the sunset

**TL;DR:** ZeroEntropy was acquired and shuts down **all** products on **September 4th, 2026**. Any brain still pointed at `zeroentropyai:*` after that date stops embedding and stops reranking. Defaults move to `openai:text-embedding-3-large` at **1280 dimensions** (unchanged width — no schema migration) and `cohere:rerank-v3.5`. New installs land there automatically. Existing brains need a config flip and a full re-embed.

**This migration is NOT opt-in.** v0.36.2.0's ZE switch was a quality upgrade the user could decline. This one is a hard deadline: doing nothing means a broken brain after September 4th, 2026. Treat a brain still on `zeroentropyai:*` as work to be finished, not a preference to be respected.

## The one thing that makes this cheap

**A migrating brain keeps its existing embedding width — 1280 for ZE-era brains.** `text-embedding-3-large` can be asked for any width in 1..3072 via Matryoshka, so 1280 is a first-class request rather than a truncation hack.

(Fresh installs are a separate case: they get OpenAI's native 1536. Do not "upgrade" a migrating brain to 1536 — see below.)

That means the expensive half of an embedding migration does not happen:

- No `ALTER ... TYPE vector(N)` on `content_chunks.embedding`.
- No dropping and rebuilding the HNSW index.
- `embedding_width_consistency` in `gbrain doctor` stays green throughout.

Only the vectors change, in place. Do **not** "helpfully" move the brain to OpenAI's native 1536 default — that reintroduces the column change and index rebuild for no retrieval benefit.

## What the agent should do post-upgrade

1. **Detect the brain's state.**
   ```bash
   gbrain models          # shows current embedding + reranker models
   gbrain doctor          # ze_embedding_health flags a ZE model
   ```
   If `embedding_model` starts with `zeroentropyai:` or the reranker model does, this migration applies.

2. **Make sure the credentials exist before touching config.** Flipping the model first leaves the brain unable to embed.

   **Do NOT use `gbrain config set` for API keys.** It writes the DB plane; the gateway reads the file plane. The write appears to succeed and the key never reaches the pipeline — the same silent-no-op that `embedding_model` has a hard guard against. `cohere_api_key` is deliberately absent from `KNOWN_CONFIG_KEYS` so the command fails loudly instead.

   Use the environment:
   ```bash
   export OPENAI_API_KEY=sk-...
   export COHERE_API_KEY=...
   ```
   or edit `~/.gbrain/config.json` directly:
   ```json
   { "openai_api_key": "sk-...", "cohere_api_key": "..." }
   ```

   Cohere issues a free **Trial** key that is rate-limited and not licensed for production use. Provision a **Production** key from the Cohere dashboard before a real cutover, or reranking will start throttling under normal load.

3. **Flip the models. Do not change dimensions.**

   `embedding_model` is file-plane canonical and sizes the schema, so `gbrain config set embedding_model ...` is **hard-refused** — by design, not a bug. Edit `~/.gbrain/config.json`:
   ```json
   { "embedding_model": "openai:text-embedding-3-large", "embedding_dimensions": 1280 }
   ```
   The reranker model is a normal DB-plane search knob and does use `config set`:
   ```bash
   gbrain config set search.reranker.model cohere:rerank-v3.5
   ```
   Leave `embedding_dimensions` at 1280. If it is already something else, keep whatever width the existing `vector(N)` column uses — matching the schema is what avoids the rebuild.

4. **Re-embed the corpus.** Old ZE vectors and new OpenAI vectors are not comparable, so search results are wrong until this finishes.
   ```bash
   gbrain embed --all
   ```
   Warn the user that search is degraded for the duration, and give them a rough size: roughly $0.13 per million tokens of content at list price. A brain of ~30K chunks lands in the low single-digit dollars.

5. **Verify.**
   ```bash
   gbrain doctor                          # all embedding checks green
   gbrain models                          # confirms both new defaults
   gbrain search "test query" --limit 5   # confirms the reranker fires
   ```

## Deployed brains: env vars win

A brain running on a hosting platform usually pins the model through environment variables, which **override** config. Flipping DB/file config there changes nothing at runtime. Update the deployment's env instead:

- `GBRAIN_EMBEDDING_MODEL` → `openai:text-embedding-3-large`
- `GBRAIN_EMBEDDING_DIMENSIONS` → leave at the existing width (1280)
- add `COHERE_API_KEY`
- retire `ZEROENTROPY_API_KEY` only **after** the re-embed completes

`gbrain ze-switch` refuses to apply when it detects a conflicting env override, and prints the offending vars. That refusal is the correct behavior — fix the env, don't bypass the guard.

## Rerank scores changed scale — retune before trusting cutoffs

Cohere normalizes `relevance_score` to `[0, 1]`, and the scale is explicitly **not** linear (0.9 is not "twice as relevant" as 0.45). `zerank-2` scored on a different scale.

Any **absolute** score threshold tuned against ZE is now meaningless. Relative ordering is unaffected, so rank-based logic (top-N, autocut's cliff detection) carries over; fixed cutoffs do not. If the user has customized reranker thresholds, flag them for re-tuning rather than silently carrying the number across.

## Don't reach for `gbrain ze-switch --undo`

It looks like the right tool and it is not. `--undo` restores the brain's *pre-ZE snapshot*, which for most brains means OpenAI at **1536d** — which forces exactly the column change and index rebuild this migration is designed to avoid. Brains created on v0.36.2.0 or later were born on ZE and have no snapshot to restore at all.

The direct config flip in step 3 is correct for both populations. `ze-switch` as a whole is vestigial after the sunset.

## If the user wants to keep zerank-2 specifically

ZeroEntropy open-sourced its weights under Apache 2.0 before shutting down, so `zerank-2` can be self-hosted and reached through the existing `llama-server-reranker` recipe. That keeps scores on the original scale and skips the retune in the section above, at the cost of running the inference yourself. Only raise this if the user asks about preserving reranker behavior exactly — Cohere is the default path.

## What changed under the hood

- Default embedding model for **fresh installs**: `zeroentropyai:zembed-1` (1280d) → `openai:text-embedding-3-large` (1536d, OpenAI's native width). Migrating brains do **not** adopt 1536 — they keep their existing 1280 and re-embed in place. The defaults constant is never read on the migration path.
- `zeroentropyai` now carries `sunset_date: '2026-09-04'`, which excludes it from `gbrain init`'s env-detection auto-pick. A stale `ZEROENTROPY_API_KEY` in the environment no longer silently provisions a brand-new brain onto a dying endpoint. Existing brains and explicit `--embedding-model zeroentropyai:zembed-1` are unaffected.
- Default reranker: `zeroentropyai:zerank-2` → `cohere:rerank-v3.5`, in `DEFAULT_RERANKER_MODEL` and in all three search-mode bundles.
- New `cohere` provider recipe. Cohere's v2 rerank wire shape matches the existing `gateway.rerank()` path exactly (`{model, query, documents, top_n}` → `{results:[{index, relevance_score}]}`), so it is pure config with no adapter shim.
- New `cohere_api_key` config key, wired file plane → `loadConfig` env merge → `buildGatewayConfig` → recipe.
- `1280` added to the openai recipe's `dims_options`. That list is enforced by `embedding-dim-check.ts`; without the entry the no-migration path is rejected by our own validator.

## What NOT to do

- Don't move the brain to 1536d "because that's OpenAI's default." It buys nothing and costs an index rebuild.
- Don't retire `ZEROENTROPY_API_KEY` before the re-embed finishes — a half-migrated brain still needs it to read nothing, but a rollback needs it to work.
- Don't carry absolute rerank score thresholds across providers.
- Don't tell the user reranking is unchanged. The provider, the scale, and the credential all changed; only the ordering semantics survived.
